## Project rules

- Data access goes only through repositories in `src/data/repos.ts` via TanStack Query hooks in `src/data/hooks.ts`; repos load the active study's budget from Supabase (`src/data/remote.ts`), apply changes in memory and write back only changed rows, so business logic stays in the repos. Every load, write and query key is scoped to the active study and workplan year (`src/data/active-study.ts`); `tx` and `wtx` capture the study and year before awaiting and sync with those ids, never through a later global lookup, and their callbacks are synchronous. Loads read the year's objectives, outcomes and activities, then lines, events and attachments through them, so another year's rows are never loaded or diffed; only lines, deliveries, indicator results, events and attachments are written back by the budget repos (parents first on writes, children first on deletes). Audit stays study-wide.
- All budget maths lives in pure `src/lib/calc.ts` (money as integer KES cents) with tests in `src/lib/calc.test.ts`. Workplan rules (year choice, overlap, tree order, duplicate codes, repeat rule) live in pure `src/lib/workplan.ts` with tests.
- The app shell renders client-only (`ClientOnly` in `__root.tsx`) because the sign-in session lives in the browser; `AuthGate` shows sign-in, then `StudyGate` picks the active study and `YearGate` the active year (each remounts the app when it changes). The year is remembered per study, defaults to the open year containing today, else the latest, and is validated against the study's years.
- Routing uses TanStack Router (spec's React Router is not supported); sub-pages use trailing-underscore files to avoid nesting. Menu: Dashboard, Activities (`/activities`, `/activities/$id`), Budget, Spending (`/spending`, `/spending/$id/record`), Settings. `/events` and `/events/$id/record` only redirect to the Spending routes, keeping search params.
- Evidence files live in the private `evidence` bucket; `fileUrl` stores `storage:<studyId>/<eventId>/<file>` and is swapped for a signed link when listed. Files uploaded before studies have no prefix; `legacy_evidence` maps them to a study, and `can_access_evidence()` checks both.
- Budget data and evidence belong to a study and are readable/writable only by its rows in `study_members` (`is_study_member(study_id)` in RLS). Ids are global primary keys, so new rows always get `uid()`, and composite FKs on `(id, study_id)` stop links across studies. Only platform admins (rows in `platform_admins`, checked by `is_platform_admin()`) can create a study with `create_study` and become its admin; being a platform admin grants no access to any study's data. `platform_admins` has no client access and starts empty: add the first one by hand with an `insert into public.platform_admins (user_id) select id from auth.users where email = '<address>'` in the Supabase SQL Editor. Signing up alone grants no access and nobody claims anything by being first. Only study admins add people (`add_study_member`), remove them (`remove_study_member`) and grant or revoke admin (`set_study_admin`), which always leaves at least one admin. `audit_log` is append-only for clients (select and insert only, so sync inserts audit rows and never upserts), and table grants for `anon` and `authenticated` are limited to what the app uses, since TRUNCATE bypasses RLS. `team_members` and `user_roles` are kept as rollback data with no client access.
- A workplan year is a `budget_periods` row (`status` open or closed). Objectives, outcomes, activities (general or site), indicators, responsible people, `activity_sites` and the study-wide `sites` list hang off it; every table has `UNIQUE (id, study_id)` and composite FKs, and codes are free text (duplicates only warn). Year rows are read-only for clients: they change only through the admin-checked, audited functions `create_workplan_year` (blank, or copying the workplan from a year in the same study, and optionally its budget lines with fresh planned events; never actuals, finance postings, receipts or evidence), `update_workplan_year` and `set_workplan_year_status`. Only study admins write years and sites; members edit workplan and budget content in open years. Triggers reject any write to workplan tables, lines, events and attachments of a closed year (resolved through the parent, so moves in or out are blocked too), and evidence uploads and deletes under a closed year's events. A study delete through `service_role` still cascades. Client controls follow `useYear().canEdit`, but the database is what enforces it. Every budget line belongs to one activity (`activity_id`, composite FK with NO ACTION, so a funded activity, outcome or objective cannot be deleted; move the lines first). A line moves only between activities of its own year, enforced by trigger. Units are free text; only the duration unit `one-off` has meaning (duration counts as 1). Components are retired: the table and `budget_lines.component_id` remain as rollback data only, with no client access, and deleting a component can never delete lines. Year dates default to the financial year, 30 September to 29 September, but are editable and not a database rule (`src/lib/workplan.ts`).
- Backend is the team's own hosted Supabase project. Schema changes are new SQL files in `supabase/migrations/` (timestamped, never edit an applied one), pushed with `npm run db:push`; regenerate `src/integrations/supabase/types.ts` with `npm run db:types` afterwards.
- Supabase credentials live in `.env.local` (untracked, see `.env.example`). Not `.env`: an old commit tracked `.env`, so checking out history can overwrite or delete it. Never commit keys; the service role key stays server-only.

- Deliveries (`deliveries`, `delivery_indicator_results`): an activity is general (not tied to a site) or site. A site activity has one delivery per selected site per round, a general one has one per round with no site. Status is `planned`, `in_progress` or `completed` (completed needs an actual date). Activity status is calculated in pure `src/lib/deliveries.ts`, never stored. Delivery is separate from spending: a spending record may link to a delivery of the same activity (`budget_events.delivery_id`), spending keeps `planned`, `done`, `cancelled` and budget maths ignores the link. A delivery is deleted, with an audit entry, only when no spending is linked and it has no proof files; activities, outcomes and objectives that hold deliveries cannot be deleted, an activity's kind cannot change, and a site cannot be removed from it while deliveries exist (archiving a site is fine and history stays). An indicator with recorded results cannot be deleted. `create_workplan_year` never copies deliveries, results or links.
- Evidence: an attachment is a receipt on a spending record (`<studyId>/<eventId>/<file>`, plus legacy paths) or proof of delivery on a delivery (`<studyId>/deliveries/<deliveryId>/<file>`), never both. `missing-evidence` on spending stays receipt-based; a completed delivery without proof gets its own flag. Storage policies check that a proof path's delivery belongs to the study in the first folder.
